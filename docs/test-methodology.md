# Test Methodology — What "Tested" Actually Means Here

This document exists because it's easy for automated test claims to quietly overstate
what was verified. Read this before trusting any pass/fail in the test report.

## The core limitation

The agent building/testing this software has no physical microphone (mouth) or ears.
It cannot acoustically speak into a real Windows microphone or listen to real speaker
output. Every "test" below is honestly labeled according to what it actually exercised.

## Test tiers, in order of how much they prove

1. **Unit tests** (`dotnet test`) — pure logic (config validation, latency math,
   feedback-loop guard). No audio, no network, no Azure. Proves the code does what it
   says on inputs that don't require hardware or a live service.

2. **File-injection pipeline tests** (`VTTranslate.LiveTest pipeline-test`) — a real
   WAV file (itself generated by real Azure TTS, so it's genuine speech audio, not a
   tone or silence) is pushed into the **exact same** `IAudioInputSource` →
   `ISpeechTranslationProvider` → playback pipeline the production app uses, via a
   test-only `TestFileAudioInputSource` implementation. This makes **real network
   calls to real Azure Speech endpoints** and validates: ASR transcript quality,
   translation quality, TTS audio is actually produced, and per-stage latency, using
   the production `AzureSpeechTranslationProvider` and `LatencyBreakdown` classes
   unmodified.
   **What this proves:** the software pipeline and Azure integration genuinely work.
   **What this does NOT prove:** that a physical microphone captures clean audio, that
   Bluetooth/USB device drivers behave correctly under NAudio, that acoustic echo from
   real speakers doesn't leak into a real microphone, or that a human would find the
   output intelligible.

3. **Manual acoustic test** (a human runs the actual WPF app, speaks into a real mic,
   listens to real output) — this is the only tier that validates physical audio
   hardware and human-perceived quality. **This tier requires the user**, not the
   agent, to execute and report results. Any claim in this report about "microphone
   input works" that isn't attributed to a human running this tier should be read as
   unverified at that tier.

4. **Meeting-app routing test** (VB-Cable + Google Meet/Teams) — requires both tier-3
   participation (a human speaking/listening) AND a second party in the call to speak
   German, or a controlled audio source routed into the call. Not achievable by the
   agent alone; documented separately with exactly what was and wasn't verified.

## Accuracy reporting

Test cases compare actual ASR transcript against the expected phrase using a loose
word-overlap check (≥60% word overlap after lowercasing and stripping punctuation),
not exact string match — real ASR legitimately varies in capitalization/punctuation.
Any mismatch is reported verbatim in the test report, not hidden or rounded away. No
claim of "100%" or any invented accuracy percentage is made anywhere in this project.
